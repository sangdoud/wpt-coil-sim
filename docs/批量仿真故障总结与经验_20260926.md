## 二、逐条：现象 → 根因 → 解决办法

### 问题 1：会话僵死——进程活着、什么都不干

**现象**
- 8 个实例在约 1 小时内**先后全部**僵死，最长白停 **9.2 小时**（run6）
- AEDT 进程仍在、`Responding=True`，但**工作集从 3.7 GB 缩到 13~846 MB**
- 日志停在 `网格: 整套优化=True` 之后，再无新增
- gRPC 全断（累计 **7996 条 `poll err`**）

**根因（两层，缺一不可）**
1. **pyaedt 的 gRPC 调用会永久阻塞**——僵死时 `is_solved` **一次异常都不抛**。
   所以任何"数异常次数"的判据都触发不了，worker 既不出点也不退出。
2. **`run_stage()` 看门狗只包住 `Analyze` 那一次调用**，包不住其后的轮询循环；
   而轮询里的 `err_streak` 会在"提取验证"兜底失败时被**清零**（原 `batch_sweep_lc.py` L546），
   死会话永远退不出循环。

**解决办法**（`C:\wpt\batch_sweep_lc.py`）
- 新增 `_aedt_cpu_seconds(pid)` / `_aedt_pid_of(d)`：用 kernel32 `GetProcessTimes`
  直接读 AEDT 进程累计 CPU 时间。**不依赖 pyaedt、不依赖 gRPC、不依赖 .profile 落盘**。
- 轮询循环内：
  - `CPU_STALL_SECS = 360`：连续 6 min CPU 时间零增长 → 判会话已死 → `kill_aedt()` + 放弃本点
  - 进程消失（返回 None）→ 立即放弃本点
  - `session_err >= 12`（连续 gRPC 抛错）→ 放弃本点
  - 轮询上限 `range(90)` → `range(180)`：**BASE 单点实测可达 41 min**，原 30 min 会误判
- 放弃本点后交给 worker 既有的「同会话 BASE 回退 / 重开会话重试」路径，**不改契约**

**判据（后续批次直接用）**

| 观测量 | 僵死 | 健康 | 是否可信 |
|---|---|---|---|
| 进程存在 / `Responding` | 存在 / True | 存在 / True | ❌ **会骗人** |
| **平均** CPU 利用率 | **15~21 核** | 8~20 核 | ❌ **最会骗人**（它是"曾经很忙"） |
| 工作集 | 13~846 MB | 3.6~5.7 GB | ⚠️ 较可靠 |
| **实时** CPU 增量（60 s） | **0.1~0.2 核** | 1~56 核 | ✅ **唯一可靠** |
| 日志年龄 | 持续增长 | < 25 min | ⚠️ 启动补偿期也会老 |

> **血泪教训**：本次靠"平均利用率 + 进程存在"**三次误判**了健康实例。**判定僵死只看实时 CPU 增量。**

### 问题 2：guard 恢复判据盲区——"要么不动，要么全灭"

**现象**：8 实例里僵死 5 个时，guard 三个判据**全不成立**（`dead` 需 worker 不足、
`all_stalled` 需全部失速、`mem_bloat` 需提交 ≥88%），于是白等数小时；
而 8 个全僵死时 → **整批强杀重启**，每实例重做几何 7~10 min。

**根因**：guard 原设计明确"单实例失速只报告不动作"（怕拖慢其余实例）——
在 1 个实例时是对的，**在 5 个同时僵死时变成彻底失能**。

**解决办法**（`_work\b1\b1_guard.py`，新增 `--relaunch-stalled`）
- `relaunch_one()`：对每个失速实例做**外科手术**——只杀它自己的 worker+AEDT，再 `_relaunch_one.py` 拉起，**完全不碰健康实例**
- 门槛可调：`--relaunch-min-stalled`（计划任务已设 **1**，即任一实例僵死就换）
- **已确认僵死快速通道**：`RELAUNCH_CONFIRMED_MIN = 25 min`——
  "CPU 零增长"是比"落盘慢"强得多的证据，不必再等 150 min 的保守线
- 生效时**抑制整批重启**（下一轮复查）

**实战验证**（09-24 12:32，无人值守）：自动识别 run3/run7 僵死 90 min → 外科恢复 → 抑制整批重启 ✅

### 问题 3：整批重启全灭——AEDT 强杀后有 3~5 分钟窗口

**现象**：guard 整批重启时，**8/8 或 6/8 实例同时**报
`Failed to start new AEDT gRPC session on port ... on machine 127.0.0.1`，一个点都解不出。

**根因（两个，都真实）**
1. **主因：杀完立刻起**。AEDT 被强杀后有约 **3~5 分钟的退出/清理窗口**，
   窗口内新建会话必然失败。guard 原来只 `time.sleep(5)`，**差一个数量级**。
   - 证据：guard 重启（间隔 5 s）3 次全灭；我手动重启（间隔 ~4 min）2 次全成功。
2. **次因：孤儿进程**。原重启只杀 `ansysedt`，留下 `3dnms` / `G3dMesher` / `ansyscl`
   半死子进程（实测抓到 `3dnms 1413 MB` + 44 MB `ansyscl`）。它们不会立刻退出，而是**慢慢老死**
   ——所以"隔一阵再重启就好了"，正是这个坑的伪装。

**解决办法**
- 新增 `_delayed_launch.py`：等 **240 s**（且 AEDT 全家族退净可提前结束）再拉起，guard 不再自己阻塞
- 重启的杀进程命令扩为 `ansysedt,3dnms,G3dMesher,ansyscl`

**判据**：**杀完必须等 ≥4 min 再起会话**；判断"干净"的方法是
`Get-Process ansysedt,3dnms,G3dMesher,ansyscl` 全为 0。

### 问题 4：重复启动器互相残杀 ⚠️ **我引入的**

**现象**：某时刻出现 **3 个启动器进程**（同一时刻启动）、worker 被杀剩 5 个，
批次反复"起不来"，持续数小时。

**根因**：我把 guard 改为调用"延迟启动器"后，整批重启全程变成
**240 s 等待 + 8 实例 × 20 s 错峰 + 会话建立 ≈ 6.5 min**，
而 guard 的"重启进行中"闸门 `LAUNCH_GRACE_MIN` 只有 **5 min**。
于是 guard 下一轮（30 min 后）判定"重启不在进行"→ **再次整批重启**，杀掉上一轮正在启动的 worker。

**解决办法**：`LAUNCH_GRACE_MIN` **5.0 → 20.0 分钟**（安全覆盖 240 s 等待 + 错峰 + 会话建立）。

**教训**：**改了重启流程的耗时，必须同步改"重启进行中"的判定窗口。**
任何"防重入"闸门的时长都要 ≥ 被保护流程的最坏耗时。

### 问题 5：完工实例被当故障 ⚠️ **我引入的（判据收紧过窄）**

**现象**：run0 在 18:23 报 `worker 结束：32 个工况，会话重启 0 次`（**正常收工**），
run3、run4、run6、run7 随后也陆续完工退出。
但 guard 因 `worker < 8` 判定"**批次已死**"→ 整批重启，**白扔 7 个健康实例的几何重建**。

**根因**：我把"批次已死"阈值从 `worker<8` 改为 `worker<4`（半数线）——
**方向对但不够**：完工退出是**设计内的正常行为**，不该算作缺口。

**解决办法（两层）**
1. `need_workers` 按**存活实例数**折算（扣除已完工实例）
2. 新增"**已完工实例识别**"：按分片比对 raw 点数，分片内工况全部满点的实例
   **从失速与缺-worker 判据中摘除**，且不再被反复尝试外科恢复（否则每次因无 lock 失败、刷日志）

**教训**：**"worker 数量少于 N"不是有效故障判据**——必须先排除正常退出。
判断"批次是否还活着"要看**所有未完工实例**是否都停了。

### 问题 6：交付清单漏报缺口（最隐蔽）

**现象**：`out\b1_manifest.json` 报出 `gaps_registered: []`、`points_missing: 0`，
而实际缺 6 个点——**把带缺口交付伪装成 256 个完整工况**，
直接违反例外表里"必须显式声明缺口"的政策。

**根因**：清单的 `known` / `miss_pts` 都从 worker JSON 派生的 `final_partial` 算，
而**整批重启会把 JSON 里 `status="partial"` 的记录重写清除**（实测批次跑完后变成 0 个）。

**解决办法**：以 **raw 反推的实际缺失点**为权威（raw 逐点落盘、跨重启不丢），
只在取不到时退回 `final_partial`；`known` 改用**例外表 ∩ 参数表**计算。

**踩坑记录**：第一次修的时候我又错了——`raws` 是 `{文件名: 已解析行列表}` 的**字典**，
我当成路径列表传给 `read_csv()` → 抛异常被 `except` 吞掉 → 每个工况都算成缺 21 点、
`points_missing: 5376`。**教训：宽泛的 `except` 会把"修错了"伪装成"没数据"。**

## 三、跨批次经验（最重要的一节）

### 3.1 六个"判据"层面的教训

1. **进程存在 ≠ 在工作**。必须用**增量**类指标（CPU 时间差），
   而不是状态类指标（存在性 / `Responding`）或累计类指标（平均利用率）。
2. **累计量会掩盖当下状态**。"平均 21 核"完全兼容"此刻 0 核"。
   凡是要判断"现在是否在干活"，一律用**两次采样之差**。
3. **异常计数救不了阻塞**。会话死在"阻塞"而非"抛错"时，`except` 分支永远不进。
   必须有一条**不依赖被测对象响应**的独立探针（这里是 OS 的 `GetProcessTimes`）。
4. **报错次数不足以判定"不可解"**。例外表自己的教训：
   曾被判"确定性不可解"的 b1_0220/b1_0022 后来被启动补偿**解出来了**。
   必须跨**足够多轮**重启重试仍失败，才能登记。
5. **单一指标会骗人，多个指标会互相矛盾**。本次"日志新鲜度 / 进程数 / 内存 / 平均 CPU"
   给出过互相矛盾的结论，我因此三次误判。**要有单一权威真值来源**（本次确立：raw 逐点文件）。
6. **宽泛的 `except` 会吞掉"我修错了"**。修 bug 时若用了 `try/except` 兜底，
   必须额外验证"修正后的数值是否符合预期"（本次 `points_missing` 应 ≈6 而非 5376）。

### 3.2 五个"运维"层面的教训

1. **杀进程必须杀全家族**。AEDT 不是单进程：`ansysedt`（GUI）+ `3dnms`（网格器）
   + `G3dMesher` + `ansyscl`（求解器）。只杀主进程 → 孤儿 → 新会话起不来。
2. **强杀后有静默窗口**。AEDT 约 3~5 min 内无法新建会话。任何"杀-重启"循环必须有 ≥4 min 间隔。
3. **"正常退出"必须与"异常退出"区分**。worker 干完分片会正常退出，
   若判据只看数量，就会"谁先干完谁害死其他人"。
4. **防重入闸门要覆盖全流程耗时**。改了流程时序就要同步改闸门窗口（问题 4）。
5. **"只报告不动作"的监控在规模化故障下等于失能**。判据设计要考虑
   **单点故障**与**多点故障**两种场景，不能只优化前者。

### 3.3 关于"我引入的问题"的反思

本次 6 类故障里 2 类是我修 bug 时引入的，共同特征是：
**改动了一个组件，但没有重新审视依赖它时序/数量假设的其它组件。**

- 改了重启耗时 → 没改"重入闸门"窗口（问题 4）
- 收紧了死亡判据 → 没考虑"正常退出"这一合法状态（问题 5）

**操作规范建议**：每次改动后，明确回答三个问题——
① 这个改动改变了哪些**时序**？② 谁依赖这些时序？③ 有哪些**合法状态**会被新判据误判？

### 3.4 关于"何时该停手"的反思

中途我多次在批次运行中做外科手术，其中：
- 有一次**误杀了正在求解的会话**（因为 `_relaunch_one.py` 起的 worker **不写 `.aedt.lock`**，
  我按 lock 找"要保留哪个会话"时拿到空值）
- 有两次为了"让补丁生效"而重启整批（代价：每实例几何重建 7~10 min）

**结论**：**批次运行中的干预，必须先在离线/空闲环境验证脚本**，
且要清楚每个实例的标识方式（lock 文件 vs PID vs 进程名）是否可靠。

## 四、下一批（如 5000 组）启动前检查清单

### 4.1 代码/脚本状态

- [ ] `batch_sweep_lc.py` 含 CPU 僵死探针（`CPU_STALL_SECS=360`、`session_err>=12`、`range(180)`）
- [ ] `b1_guard.py` 含：`--relaunch-stalled`、`relaunch_one()`、已完工实例识别、`LAUNCH_GRACE_MIN=20`
- [ ] `_delayed_launch.py` 存在且 `_relaunch_one.py` 在 PATH 位置
- [ ] `b1_deliver.py` 的清单缺口用 raw 反推（打补丁后**必须验证 `points_missing` 数值合理**）
- [ ] 计划任务 `b1_batch_guard` 参数 = `--restart --relaunch-stalled --relaunch-min-stalled 1`
- [ ] 改过 `batch_sweep_lc.py` 后**必须重启 worker 才生效**（用启动时间比对确认）

### 4.2 环境

- [ ] 杀进程命令覆盖 `ansysedt,3dnms,G3dMesher,ansyscl`
- [ ] 任何整批重启：**杀 → 等 ≥240 s（或确认全家族退净）→ 再起**
- [ ] 磁盘余量 > 40 GB（页面文件需增长空间）
- [ ] HPC token / 并发席位 ≥ 目标并发数

### 4.3 监控阈值（照抄）

| 指标 | 健康 | 报警 | 处置 |
|---|---|---|---|
| 实时 CPU 增量（60 s） | 1~56 核 | **< 1 核 且 日志 >20 min 未更新** | 判僵死 → 外科恢复 |
| 单点耗时 p90 | ≤ 9 min | > 13 min | 查并发/内存，考虑减实例 |
| 网格器崩溃 | ≈2 次/h | > 4 次/h | 关注点失败率，不需动作 |
| 可用内存 | > 8 GB | < 2 GB | 减实例 |
| 提交量 | 53~75% | ≥ 88% 且多实例失速 | 内存耗尽自救 |
| 日志年龄 | < 25 min | > 90 min | 失速（但注意启动补偿期合法） |

### 4.4 收尾流程

```powershell
# 1) 确认全部 worker 正常退出、进程清零
Get-Process ansysedt,3dnms,G3dMesher,ansyscl -EA SilentlyContinue
# 2) 权威缺口（不要用 b1_status 的 ETA，它不读例外表）
python -c "..."   # 按 plan 口径 + raw 反推
# 3) 有缺口 → 先跨多轮重试；确认不可解再登记 b1_partial_exceptions.json
# 4) 交付
python b1_deliver.py --root <root> --batch b1
python b1_accept.py  --root <root> --batch b1
# 5) 校验清单里 points_missing 与实际缺口一致（防漏报）
```
