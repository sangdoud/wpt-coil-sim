## 3. 批次机制（新会话必读）

```
contract_launch.py 8 --batch b1 --root …\b1 --boxx 420 --merge
   ├─ 分片：b1_plan.csv 按行号交错 → b1_plan_shardK.csv（每实例 32 工况）
   ├─ 副本：Projecttonight_ref.aedt → Projecttonight_b1_runK.aedt（清 .aedtresults）
   └─ 起 8 个 contract_worker.py（WPT_RUN=K，错峰 20 s）

每个 worker 每工况：
   几何重建（几何完整性硬校验：铁氧体条数 + Region）
   → 21 点半扫（x_i = i·S/40，S = Lc(2+g)）
   → 逐点求解（OPT 口径；失败则同会话切 BASE 口径重试；再失败则重启会话重试）
   → 每点结果立即落盘 b1_raw_runK.csv（mesh 列标记该点口径）+ 清理求解数据
   → 工况结束若仍缺点 → 立刻用 BASE 口径补齐
```

**口径（不可改）**：几何 `PATH_MODE=ring`（拐角修正版）｜空气域 X±420 / Y[−134.94,161] / Z[−45,75]｜
网格 OPT=柔性+⑥+pref10+rres1e-5，闸门 `OPT_MIN_GAP=1.5mm`，不通过则整套 BASE（pref5+rres1e-6）。
详见《batch1_交付口径说明_20260919.md》。

> **今后登记缺口前，必须先确认已跨足够多轮重启重试仍失败**，别急着下"不可解"的结论。
> （`b1_0081` 就是按这条新标准办的：已跨 2 轮重启重置仍失败才登记。）

## 9. 磁盘：为什么掉得快，以及定时清理（第三次交接新增）

### 9.1 主因不是仿真漏文件

2026-09-19 实测：C: 可用空间从早上 131.3 GB 掉到 19:43 的 113.8 GB（一天约 16 GB），
但**不是批次在漏文件**。逐项排查结果：

| 占用项 | 实测 | 判断 |
|---|---|---|
| `C:\pagefile.sys` | **46 GB**（实际使用 22.9 GB，峰值 23.1） | **主因**，系统自动管理、随内存压力增长 |
| 8 份 `.aedtresults` | 1.88 GB | 与"稳态 ≈1.8 GB"一致，正常 |
| `%LOCALAPPDATA%\Temp\<n>` | 2.25 GB | 活跃会话暂存，`b1_disk.py` 已托管回收 |
| `CrashDumps`（3dnms 转储） | 0.75 GB / 10 份 | 每份 76.6 MB，随崩溃累积 |
| 回收站 / 卷影副本 / 内核转储 | 0.18 GB / 0 / 无 | 可忽略 |

机制：8 实例 AEDT + 网格器把提交量推到 **66/77 GB**（物理仅 31.6 GB），
系统自动管理的页面文件因此涨到 46 GB 并仍在增长。

### 9.2 为什么要盯磁盘余量（不只是省空间）

`pagefile.sys` 是求解器提交内存的**最后兜底**：

```
磁盘没空间 -> 页面文件长不动 -> 提交分配失败 -> 求解器 OOM 死
```

而 OOM 死的症状会和《b1_失败签名诊断》里的 `3dnms.exe` 崩溃**混在一起，极难区分**。
实测吻合：20:03 磁盘触底 111.9 GB，**20:30 / 20:36 就各崩了一次 3dnms**。
故 `b1_guard.py` 与 `b1_clean.py` 都加了 **磁盘可用 < 40 GB 报警**（`DISK_ALERT_GB`）。

## 10. 内存耗尽：整批卡死的根因与两项修复（2026-09-21）

### 10.1 症状

2026-09-21 凌晨，**8 个实例在 01:50~06:00 之间陆续全部冻死，白停 6~10 小时**。
表现为 guard 报「整体失速」，但：

- worker 进程**都还在**（不是进程死亡），日志**零新增**
- worker 与 AEDT 的 **30 秒 CPU 增量都是 0.00 秒**（不是 gRPC 死循环那种"疯狂报错"）
- 日志都停在同一位置：`网格优化=True` 或 `Saved correctly` 之后

### 10.2 根因：AEDT 会话私有内存膨胀 → 压爆页面文件

```
8 个 AEDT 私有内存合计 ≈ 60 GB   ← 单个最高 13 GB（会话存活 ~12 h）
本机物理内存 = 31.6 GB            ← 只有它的 1/1.9
        ↓ 全部压进页面文件
pagefile  46 GB → 59.4 GB（峰值使用 45 GB）
        ↓
提交量 85.5 / 89.6 GB（95%，越过 92% 报警线）
        ↓
换页失控 → 8 个会话陆续冻死
```

**关键相关性：会话存活时长 ↔ 私有内存**。实测：~15 h 的会话私有 10.2 GB、
~12 h 的 13.0 GB。所以这是个**「跑 10~15 小时 → 内存爆 → 整批停」的循环**。

> 诊断要点：**别只看工作集**。8 个 AEDT 的工作集看着只有 17 GB（很正常），
> 但**私有内存合计 ~60 GB** 才是提交量的真凶。用
> `Get-Process ansysedt | Select Id,WorkingSet64,PrivateMemorySize64` 看。

### 10.3 两项修复（都已落地并验证）

**修复 A：主动会话轮换（治本）** —— `contract_worker.py`

在**工况边界**（此处本来就要重建几何，轮换代价近零）检查会话存活时长，
超过 `WPT_SESSION_MAX_H`（默认 **7 h**）就主动重开会话：

```
[3/32] === b1_XXXX === 【主动轮换】会话已存活 7.4 h（阈值 7.0 h），在工况边界重开会话以释放内存
  轮换完成，新会话 pid=NNNNN
```

- 实现：`recycle_session()`（紧跟 `open_session()` 之后），在 `SESS["t0"]` 记会话起始
- 关闭轮换：`WPT_SESSION_MAX_H=0`
- 重开失败**不会让 worker 崩**（返回 False、保留旧会话继续，仍有 guard 兜底）
- 决策逻辑已单测 4 条路径：不轮换 / 轮换 / 关闭 / 重开失败（全部通过）

**修复 B：guard 自动兜底** —— `b1_guard.py` + 计划任务

1. 计划任务 `b1_batch_guard` 参数加上 **`--restart`**（原先故意不带，卡死后不会自救）
2. ⚠️ **同时修掉两个会让它误杀批次的缺陷** —— 这两个叠加会**无限重启死循环**：
   - **启动器窗口期**：启动器按 20 s 错峰起 8 个实例、全程 ~2.5 min。这期间 worker 数
     不足 8，若 guard 恰好在此窗口再跑一次，就会把**正在启动**的实例又杀掉重启
     → 加闸门：**启动器已在运行则跳过**（记「重启进行中」）
   - **失速误报**：原判据只看 **raw 落盘时间**，但 worker 重启后的【启动补偿】阶段
     会连续重解缺点工况（每点 BASE 可达 ~20 min）**合法地不写 raw**，几何+网格本身
     也常 >45 min → guard 会把"正在干活"判成失速 → 阈值 **45→90 min**，并改为
     **取「raw 落盘」与「worker 日志写入」中较新者**作为活跃度
3. 实测验证：修正后健康批次报「健康 ✓ / 无需重启」；
   构造"启动器在跑 + 整体失速"场景时正确输出「需要重启，但启动器已在运行 → 跳过」

### 10.4 ⚠️ 兜底机制曾经完全失效 —— 2026-09-22 第二次事故（两处已修）

#### 缺陷 1：判据要求"全部失速"，而内存耗尽是**陆续**冻死

`--restart` 原先只判 `dead or all_stalled`。2026-09-22 实测：内存耗尽时实例**陆续**冻死
—— run6 05:31 先停，run1 06:29、run7 07:01、run2 07:38、run0 07:41、run5 08:16、
run3 08:40 依次跟上，而 **run4 一直正常出点**，于是 `all_stalled`（要求**全部**失速）
**永远不成立** —— 7 个实例白停 4.5~6.5 小时，guard 每 30 分钟照报「健康 ✓ / 无需重启」。
**实测损失：05:01~11:34 只产出 80 点（12.2 点/h，正常 40 点/h），少产出 182 点 ≈ 4.5 小时。**

**修法**：新增第二条独立判据（不依赖"全部"）

```python
# 提交量 ≥ 88% 且 ≥5 个实例失速 -> 判定内存耗尽，触发重启
mem_bloat = (commit_pct >= 88.0 and len(stall) >= 5)
if args.restart and (dead or all_stalled or mem_bloat): ...
```

- 取 **88%** 的理由：92% 是报警线，实测"已被冻死"的批次提交量在 92~95%；
  88% 留余量，且单靠 88% 不会误触发（健康时提交量 53~75%）
- **实测验证**：干跑立即触发 `判定：内存耗尽（提交 92.6% ≥ 88% 且 7/8 实例失速）`，
  随后实跑成功重启恢复（提交量 92.5% → 34.9%）
- 误触发风险：若某次重启时恰有 ≥5 实例因几何重建而"失速"、且提交量 ≥88%，会重启整批
  —— 只损失各实例当前 in-flight 点，**远小于白停 6 小时的代价**，故接受

#### 缺陷 2：🔴 "重启进行中"闸门写成"启动器是否存在"，**永久阻止了所有重启**

10.3 为防重启死循环加的闸门，原写法是 `int(n_launch) > 0` 就跳过 ——
**错得离谱**：`contract_launch.py` 末尾 `for k,p in enumerate(procs): p.wait()`
会**等 8 个 worker 全部结束才退出**，即**整个批次期间启动器一直存在**
（实测 pid=40920 已存活 **1429 分钟**）。

后果：`n_launch > 0` **恒成立** → 闸门**永久拦截每一轮重启** →
2026-09-22 修好判据 1 后首次实跑仍被拦，恢复被彻底挡住。
**这是把"安全网"变成了"永不动作"，比没有兜底更危险**（因为看起来有兜底）。

**修法**：改用**启动器年龄**判断"重启是否正在进行"

```python
LAUNCH_GRACE_MIN = 5.0     # 错峰起 8 实例约 2.5 min，取 5 min 余量
restarting = float(launch_age_min) < LAUNCH_GRACE_MIN   # 只拦"刚启动"的启动器
```

（查询取 `Sort-Object CreationDate -Descending | Select-Object -First 1`，即最新那个。）

**实测验证**：启动器年龄 1429 min > 5 → 不再拦截 → 重启成功执行。

> **教训**：两道防线必须**分别验证会触发**，不能只看代码"看起来对"。
> 缺陷 2 恰恰是在验证缺陷 1 的修复时才暴露的 —— 若只做静态审查，会带着
> "有兜底"的错觉继续跑几天。

### 10.5 仍需人工留意的边界

- **主动轮换（10.3 修复 A）至今从未被观测到触发**：当前工况下会话平均只活
  1.5~3.5 小时（被几何重试 / gRPC 僵死自愈 / 崩溃恢复等路径频繁重建），
  达不到 7 h 阈值。**故当前真正的保护是 guard 兜底 + 会话自然高频更替，
  而不是轮换机制**。轮换作为"万一某会话真活过 7 h"的兜底保留，
  但**未经实测生效**，不应记作已验证。
- 轮换阈值 7 h 是**估计值**（依据：12 h 会话私有内存已到 13 GB，膨胀渐进）。
  若出现"跑十几小时卡死"，把 `WPT_SESSION_MAX_H` 调小（如 4~5）。
- guard 兜底延迟：内存耗尽判据最坏 = 失速阈值 90 min + 巡检周期 30 min ≈ **2 小时**。
- **根因未除**：AEDT 会话为何膨胀到 13 GB 没有查（是泄漏还是缓存策略），
  轮换/重启都只是绕过。
