### 1.4 最贵的六条判据教训（第二轮继续适用）

1. **进程存在 ≠ 在工作**。`Responding=True`、工作集 3.6 GB 都可能是尸体；只有**两次采样之差**（实时 CPU 增量）可信。第一轮靠"平均利用率 + 进程存在"**误判健康实例 3 次**。
2. **累计量会掩盖当下**。"平均 21 核"完全兼容"此刻 0 核"。
3. **异常计数救不了阻塞**。必须有一条**不依赖被测对象响应**的独立探针（这里是 OS 的 `GetProcessTimes`）。
4. **报错次数不足以判定"不可解"**。曾被登记为"确定性不可解"的 `b1_0220`/`b1_0022` 后来被【启动补偿】解出来了。登记缺口必须跨**足够多轮**重启仍失败。
5. **单一指标会骗人，多指标会互相矛盾**。必须有**单一权威真值来源**——本项目的答案是 **raw 逐点 CSV**。
6. **宽泛的 `except` 会把"我修错了"伪装成"没数据"**。第一轮修清单缺口时，把 `raws` 字典当路径列表传，异常被 `except` 吞掉，`points_missing` 报成 5376（真值应为 6）。

## 6. 出问题时的处置手册（第一轮修订版）

| 症状 | 判据 | 动作 |
|---|---|---|
| 某实例长时间不出点 | guard 报失速（>90 min） | **先看 `b2_guard.log` 的崩溃行**。实测时间常数：崩溃→点失败 **+106 s**；重开会话→就绪 **≈7.2 min**；三级回退全程 **≈20 min**。**20~35 min 无新点属正常恢复** |
| 失速类型 A：gRPC 会话僵死（**会自愈**） | worker 日志**仍在快速增长**，内容全是 `GrpcApiError: GetAvailableReportTypes` | **不要动**，等 20~45 min 自愈（轮询循环有界：180×20 s） |
| 失速类型 B：worker 完全静默（不自愈） | 30 秒内日志 0 行、worker 与 AEDT 的 CPU 增量都是 0.00 秒 | guard 的外科恢复（已配 `--relaunch-min-stalled 1`）会在 CPU 探针确认 25 min 后自动换掉它；**不要**跑整批 `--restart` |
| guard 报"批次已死" | worker 数低于**未完工实例数**的半数线 | guard 自动 `--restart`（断点续跑，最多损失 in-flight 点）；注意今天已修：**全机口径的 PowerShell 抖动不再被当成"已死"** |
| guard 报"全部完工" | 所有实例满点，或所缺点都在例外表 | **不要重启**。若还有未登记缺点，先按 §5-R7 判定是否登记 |

| 出现新的 partial 工况 | `b2_deliver.py` 报"无未登记的缺口"失败 | **不要**直接加进例外表。先查 `b2_worker_runK.log` 的「补偿仍失败」+ 崩溃时刻对齐，确认规定口径下不可解再登记 |
